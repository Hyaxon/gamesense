# ADR 1: Shared Domain Model Conventions

## Status
Accepted

## Context

GameSense is split across a Java backend, a Python prediction service, and a JavaScript/TypeScript frontend. Without agreement on identifier strategy, wire-format field naming, timestamp representation, and enum representation, each component risks representing the same entity (`Team`, `Game`, a prediction) differently, making the API contracts and data schema built on top of the shared domain model (`docs/architecture/domain-model.md`) inconsistent across languages.

## Decision

- **Identifiers:** every shared entity has a canonical `id` as a UUID v4 string, generated by whichever component first creates the record (typically the backend during ingestion). `Team` and `Game`, which originate from Adam's externally provided CSV/JSON data feed, additionally carry an `externalId` holding the feed's own identifier for that record. This keeps ingested data traceable back to its source without requiring every component to adopt the feed's ID format as the canonical one, and without requiring the feed's IDs to be globally unique or stable across seasons.
- **Wire format:** JSON exchanged between components uses `camelCase` field names. Java and JavaScript/TypeScript use this directly; the Python prediction service converts to/from `snake_case` at its service boundary rather than exposing snake_case over the wire, so no component has to special-case another's naming convention.
- **Timestamps:** ISO 8601 strings in UTC, in fields suffixed `At` (e.g. `scheduledAt`).
- **Enums:** represented as `UPPER_SNAKE_CASE` strings (e.g. `IN_PROGRESS`), so the same literal values work unmodified as a Java `enum`, a Python `Enum`, and a JS string union — no per-language translation table needed.

## Consequences

- Positive: one schema document and one set of shared JSON Schema files can describe the data for all three components; new entities added later should follow the same conventions without a fresh design discussion.
- Positive: ingestion code can preserve feed identifiers for debugging/auditing without those identifiers leaking into the rest of the system as the primary key.
- Trade-off: the Python service takes on a small amount of camelCase/snake_case conversion at its API boundary that a snake_case wire format would avoid; this was accepted since it keeps the wire format consistent for the two majority consumers (Java, JS) and keeps the conversion localized to one place per Python service rather than scattered across every consumer of Python-originated data.
- Follow-up: as REST API contracts and the persistence layer are defined in later tickets, they should reference `docs/architecture/domain-model.md` as the source of truth for field names and types rather than re-deriving them.
